# TLS: talking to https servers

UbiqOS can open a TLS connection to a server on the internet and check that it
is the server it claims to be. `fetch` uses it:

    ubiqos:/> fetch https://example.com/
    HTTP/1.1 200 OK
    ...
    fetch: TLS 1.2, TLS-ECDHE-ECDSA-WITH-CHACHA20-POLY1305-SHA256, certificate checked

and a module can use the same thing through `lib/tls/ubiqos_tls.h`.

## What it is

The Pico SDK's Mbed TLS 3.6, configured as a TLS 1.2 client and nothing else
([`lib/tls/ubiqos_mbedtls_config.h`](../lib/tls/ubiqos_mbedtls_config.h)):
ECDHE key exchange with ECDSA or RSA certificates, AES-GCM or
ChaCha20-Poly1305, curves P-256, P-384 and X25519. That is what servers offer a
client today. TLS 1.3 needs Mbed TLS's PSA crypto core and is not built yet;
servers still offer 1.2 beside it.

It runs in the module that uses it, not in the kernel. The kernel is linked to
run from SRAM and has no room for it; a module has PSRAM, and a handshake wants
around 60 kB. `fetch` takes 32 kB for data and stack and a 192 kB heap, both
from PSRAM, and its code grows by about 155 kB; the roots are a separate
module of 19 kB, shared by every client.

## What it checks

Every connection is checked, and one that fails is not made: there is no
option to skip it.

- **The chain** must end at one of the roots built in, or one in
  `/sd/certs.pem`.
- **The name** the certificate was issued to must be the host that was asked
  for.
- **The dates**: the certificate must be valid now, which needs the wall clock.
  SNTP sets it shortly after the network comes up; until then a connection is
  refused with a message saying so. The clock is read from `/var/utc`, seconds
  since 1970 in UTC.

It does **not** check revocation. There is no OCSP or CRL lookup, so a
certificate its authority has withdrawn is accepted until it expires.

Measured on the Fruit Jam against badssl.com: a valid chain is accepted; an
expired certificate, a wrong host name, a self-signed certificate, an unknown
root and a TLS 1.0 server are all refused, each with the reason. On RISC-V the
valid chains and the expired and wrong-host cases were run again, with the
same results.

## The roots

Twenty, in the data module `tlsroots`
([`modules/tlsroots/tlsroots.c`](../modules/tlsroots/tlsroots.c)), resident in
flash beside the system: Let's Encrypt, DigiCert, Google Trust Services, GlobalSign, Amazon, Sectigo
(USERTrust), Microsoft, SSL.com and GoDaddy/Starfield -- the issuers behind
most of the web, the large clouds, and Cloudflare. They are generated by
[`tools/make_roots.py`](../tools/make_roots.py) from macOS's trust store, each
pinned by its SHA-256 fingerprint so that a change in the source stops the
script rather than slipping into the build.

A data module is one copy for every program that uses it, and it can be
replaced without rebuilding anything. Each connection first asks the card for a
`tlsroots` module, and the module directory keeps whichever copy has the higher
revision -- the way OS-9 was patched with a newer module in a spare EPROM
socket. So roots are brought up to date in the field like this:

1. Change the list in `tools/make_roots.py` and run it.
2. Raise `REV` on the `tlsroots` line in `CMakeLists.txt`, and build.
3. Copy `build/tlsroots.mod` to the root of the card.

A copy on the card with the same or a lower revision than the one in flash is
ignored, with a line on the console saying so.

`tlsroots` is marked `UBIQOS_ATTR_PLAIN`: plain data, not a device descriptor.
Without the mark the kernel would have taken it for one at boot, as it takes
every other data module. A program reaches such a module with
`ubiqos_data_link` and lets it go with `ubiqos_data_unlink`.

For a server whose root is not among them, put that root in PEM form in
`/sd/certs.pem` on the card. Several can be concatenated there.

## Where the keys come from

The RP2350's TRNG, through `ubiqos_random_trng` (`SYS_RANDOM` with
`UBIQOS_RANDOM_TRNG`). It returns raw ring-oscillator samples taken the way the
SDK's `pico_rand` takes them; `lib/tls` folds eight of them into each byte it
gives Mbed TLS, which hashes them into its entropy pool before a CTR-DRBG is
seeded from it. The older `ubiqos_random` stays what it was: fine for an
identifier, not for a key.

## Using it from a module

The module must be `NEWLIB`, and CMake adds the rest:

```cmake
ubiqos_add_module(mymod modules/mymod/mymod.c NEWLIB)
ubiqos_module_use_tls(mymod)
```

```c
#include "ubiqos_tls.h"

char why[200];
ubiqos_tls_t *t = ubiqos_tls_open("api.example.com", 443, why, sizeof why);
if (!t) { /* why says what went wrong */ }
ubiqos_tls_write(t, request, request_len);
int32_t n;
while ((n = ubiqos_tls_read(t, buf, sizeof buf, 5000)) > 0) { /* ... */ }
ubiqos_tls_close(t);
```

A module that uses it should ask for memory as `fetch` does:
`UBIQOS_MEM_SIZE(32768)` and `uint32_t ubiqos_heap_bytes = 192u * 1024u;`.
